## 一、总体结论
**这是一个工程质量显著高于平均水平的项目，可以放心在所述范围内使用。** 架构清晰（engine 库 / cli 应用 / mod 独立构建三段式）、文档异常完备（handoff.md 机读决策记录 + 分歧账本 DIVERGENCES + 面向 AI 的 agent-guide）、测试与平台验证有据可查。本次审查**未发现任何 P0（安全/数据损坏）问题**；发现 **P1 × 3、P2 × 7、P3 × 9**（详见第三节），均为可修复的边界与健壮性问题，不影响主流程可用性。
两个安全核心问题都有明确肯定结论：
1. **模拟器无文件系统逃逸**：Lua 程序运行在纯内存 MemoryMount 上（经 CC:T 官方 ComputerEnvironment 接口接入，未绕过其沙箱层），fixture 路径拒绝 `..`，外设代码无磁盘 I/O——被测程序不可能触碰真实文件系统。
2. **cct-live mod 的 HTTP 面收得很紧**：写死只绑 `127.0.0.1`（IPv4 显式绑定，不可配置）、24 字节 SecureRandom token + 常量时间比较、Host 头白名单防 DNS rebinding、无 CORS 头使浏览器侧 CSRF 不可行、64KB 请求体上限；AI 对游戏电脑的文件读写全程复用 CC:T 自己的 `createRootMount()` 沙箱（含磁盘配额），`..` 显式拒绝、/rom 只读、写入默认关闭——**服务器真实文件系统不可达**。

## 三、发现清单
严重度定义：P0=安全/数据损坏；P1=行为错误或与声明不符，建议修复后发布；P2=健壮性/可维护性；P3=小问题。
标注 ✅ 的条目已由父审查复读代码现场核实；标注 ⚠️ 的条目机制在代码上成立，但依赖 Windows 文件语义，建议先写复现用例确认。
### P1（3 条）
1. **✅ [cli] McpServer.java:248/258 — 超时/取消后立即删除子进程输出重定向文件，Windows 上会抛 IOException。**
   `finally { Files.deleteIfExists(stdoutFile); ... }` 在 `destroyForcibly()` 之后立刻执行；Windows 上 ProcessBuilder 重定向文件的句柄（父进程自持 + 子进程继承）尚未释放，删除抛 AccessDeniedException，把「cct-run did not finish within …」超时文案顶掉成 internal error，并泄漏 %TEMP% 临时文件。修复：kill 后 `process.waitFor()` 再删，或删除失败降级记日志。
2. **⚠️ [mod] ComputerTrace.java:143（配合 rotate，:143-156）— trace 轮换与 HTTP 读取竞态，Windows 上可致该电脑 trace 本会话永久停写。**
   `rotate()` 执行 `Files.move(file, oldFile, REPLACE_EXISTING)`；同时 HTTP 线程经 `lines()`（Files.lines）正在读旧段文件。Windows 上 replace 一个仍被打开的文件会失败；失败沿 `record()` 的 catch 变成 `closed = true`（"tracing for this computer stops"），此后该电脑所有记录静默丢弃、无重试。触发链真实存在：README 实测含 Windows 单人游戏 + AI 高频轮询 trace/30 台接管每分钟 80MB。修复：轮换改写新文件名，或 rotate 失败时延后重试而非置 closed。Linux 上 rename 语义不同，故现有 Linux 基准测不出。
3. **✅ [mod] LiveSession.java:190-205 — attach 无任何玩家确认步骤，README「在玩家同意后接管」不成立。**
   attach 直接生效，聊天广播（"AI 已接管…可收回"）是事后告知；`control.chat=false` 时除日志外完全静默。mod/README 的「公开提示+随时收回」措辞与实现一致，但主 README 的「玩家同意后」是产品级承诺缺口。Lua 程序无法自行触发接管（唯一入口是持 token 的 HTTP），风险限于本机持有 token 的 AI 客户端。修复：attach 先入 pending 并广播，玩家 `/cctlive allow <id>` 后生效；或改掉主 README 措辞。
### P2（7 条）
1. **✅ [engine] Runner.java:126 — OOM 击中报错渲染路径时误报 shutdown(exit 3)。** `out_of_memory` 判定依赖 harness 的 `report.done` 已把 message 写入；若堆尽发生在 printError/traceback 渲染中，done 不会执行，结局按 shutdown 处理。修复：shutdown 分支回查 RecordingMachine 的 vm_error note。
2. **[engine] Trace.java:30/78 — 模拟器 trace 无大小上限**（README R5 已自认）：最坏 ~1.2KB/刻 ≈ 86MB/时/run，跨运行累积。与路线图第 4 项（trace 上限 + `cct-run clean`）对应，发布前应补。
3. **[mod] LiveHttp.java:689 — 服务器线程任务超时不取消。** `server.submit(...).get(5s)` 超时返回 503，但任务仍会执行；对 attach/write/event/power 等有副作用操作，客户端重试会重复动作。修复：超时取消 Future 或引入 pending/unknown 语义。
4. **[mod] ComputerSnapshots.java:98 — save 覆盖同名快照非原子。** 先删旧目录再写新内容，中途失败（磁盘满/占用）则快照全丢。修复：写临时目录成功后原子改名。
5. **[mod] PeripheralQuery.java:37 — 只读白名单仅按方法名正则，不校验线程注解。** 非主线程泛型外设方法会在服务器线程执行，与电脑线程并发访问同一外设（CC:T 对泛型方法无线程安全保证）。修复：按 mainThread 标记分流，或 README 明示窗口。
6. **[cli] LiveTools.java:520/597 — in-process 工具拿不到 Call 对象，`notifications/cancelled` 对 wait/lua/trace 等无效**，最长多跑 ~120 s。
7. **[cli] McpServer.java:113 与 :46 — 一律拒绝批量请求与协议版本 2024-11-05（允许批量）的声明矛盾**，建议协议版本列表去掉该项或补文档说明。
### P3（精选 9 条，全量见模块附录）
- [cli] McpServer.java:103 readLine 无单行长度上限（恶意/失控客户端可耗内存；本地场景影响小）
- [cli] McpServer.java:108 Gson 宽松模式接受非严格 JSON
- [cli] McpServer.java:148 请求 id 复用时 active.put 覆盖旧 Call，旧请求不可取消
- [cli] LiveTools.java:540 rememberScreens 吞异常，基线失败静默降级可能让 wait 误匹配旧画面
- [mod] LiveHttp.java:721 `Host` 头缺失放行（README「只接受 Host 为…」略强于实现）
- [mod] LiveHttp.java:80 固定 2 个 HTTP 线程 + 全文件扫描读取，两个并发重请求可阻塞轮询数秒
- [mod] LiveSession.java:270 token.txt 未设 0600（Linux 多用户主机上其他用户可读取后完全控制电脑）
- [engine] Runner.java:90 程序与 fixture 同名文件静默覆盖；RecordingMachine.java:63-68 程序自设同值 setting_changed 会被误标 `harness:true`
- [docs] handoff.md:12 状态行「41/41 tests」已过期（实际 54/54）；mod/README.md:84「15 个 cct_live_* 工具」实为 16——handoff 是带日期的机读快照，但机器审阅者会当现状读，建议下次发版同步
