测试设计见 [`joint-test-orders.md`](joint-test-orders.md)。本报告依据交付的会话记录（DeepSeek Harness 导出）和代码包。**维护者验收（A1～A10）还没有全部完成**，下文“结果”一节只写 AI 自己做过的验证；验收完成后补上。

| 项目 | 数据 |
|---|---|

## 逐条回答测试问题

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 是否一开始就把轮询外设和处理事件分开 | **是**。第一版 `order.lua` 的第 2 行就写明“三个协程：listener（只收事件）、worker（处理聊天和触摸）、poller（读写硬件）”，用 `parallel.waitForAny` 运行，和 Skill 1.2.0 `events-and-concurrency.md` 里的标准结构一致；AI 写代码前读了这一篇。**花在事件丢失上的时间：0**（联合测试 3 第 2 次约 34 分钟） |
| Q2 | 是否在模拟器里用 `scripted` 描述模组外设，数值取自实机 | **是**。转速控制器、应力表、转速表、显示链接器、聊天框、玩家探测器、红石继电器全部用 `scripted`；数值来自实机探测（容量 16384、转速 −256、显示链接器 6×22）；用时间线的 `method` 动作模拟应力升到 16000；另做了“重启续跑”的 fixture（预置状态文件）。**例外**：注入中文聊天指令时变成了 `?`，AI 没有查说明里注入 UTF-8 的写法，而是给程序加了英文别名（`!order` 等），模拟器里只测了英文指令 |
| Q3 | 程序运行时是否用 `cct_live_peripheral` 和 trace 过滤 | **部分**。trace 过滤用了：`cct_live_trace` 按 `method` / `peripheral` 过滤 8 次，`cct_trace` 用 `contains` 3 次。`cct_live_peripheral` **一次也没用**：外设探测都在程序启动前用 `cct_live_lua` 做完；程序运行时要改文件，就先用 `terminate` 停下程序（共 4 次），再用 `cct_live_lua` 改 |
| Q4 | 是否自己发现“反直觉”行为 | 见下表，6 个埋点都处理了；中文输出的问题是玩家反馈后才发现的 |
| Q5 | 重启后状态是否正确恢复 | AI 自测：模拟器“基准 130、已完成 3/5，重启后补到 5”；实机 3 次 `reboot`，订单 #4 在 486/1000 处继续完成，没有归零或重复计数。**还要等维护者验收 A4**（退出世界再进入） |
| Q6 | 和联合测试 3 相比 | 见最后一节 |

### 埋点和意外发现

| 埋点 / 发现 | AI 的处理 |
|---|---|
| 1 转速越高应力越大 | 实测：粉碎线单独全速就是 100%，两条线同时开 24576 > 16384 SU，整网停转。所以订单改为串行；过载时降到约 218 rpm |
| 2 转速带符号 | 记录了转速表的 −256，配置里每条线有 `sign` |
| 3 保险库格子数 | 用 `size()` 读实际容量（1080 格） |
| 4 聊天框频率限制 | 先读了 `getOperationCooldown`；回复放进发送队列，失败后 0.4 秒重试 |
| 5 中文指令要用 `messageUtf8` | 读 `ev[6]`（messageUtf8），没有时退回 `ev[3]`。实机上玩家的中文指令能正常执行 |
| 6 不能覆盖 `startup.lua` | 读了 `/rom/startup.lua`，发现 `/startup/` 目录里的文件也会在开机时运行，于是建了 `/startup/order`；还发现玩家原有的 `startup.lua` 本身有语法错误，报告了但没有改 |
| 7 显示链接器 | 用了 `getSize/clear/setCursorPos/write/update`，但没有让玩家确认显示板上的内容 |
| 意外：继电器开 = 离合器断开 | 实测确认，写进代码注释和报告 |
| 意外：转速控制器 1 不起作用 | 把它从 256 设到 0，铁板产量不变；改控制器 0 时产量减半。报告里说明了 |
| 意外：原料箱不是直接供料 | 原料数量在生产时不变，所以“缺料”改为“12 秒没有新产物”判断 |
| **中文输出乱码** | 程序把 UTF-8 字节直接传给 `sendMessageToPlayer`，聊天栏显示乱码。trace 里早就能看到参数是 `å·²…`（模拟器第 63 分钟、实机第 68 分钟都看到过），AI 没有认出来。玩家反馈后，AI 改用 `sendFormattedMessageToPlayer` 加 JSON 文本组件（中文写成 `\uXXXX`），玩家确认正常 |
| `sendMessageToPlayer` 的参数 | 按文档传 7 个参数时报 `bad argument #4`，改为两个参数。`scripted` 外设不检查参数类型，所以模拟器测不到这一点 |

## 结果（AI 自测，维护者验收待补）

| 项目 | 模拟器 | 实机 |
|---|---|---|
| 下单 → 生产 → 计数 → 完成通知 | 是 | 是（面粉 5、30、1000，铁板 200） |
| 过载保护 | 是（时间线让应力升到 16000） | 是（100% → 218 rpm） |
| `!转速` 生效和越界拒绝 | 是 | 是 |
| 权限（别人发指令） | 是 | 否 |
| 触摸按钮 | 是 | 是（玩家点击） |
| 外设断开 | — | 是（玩家拔插有线调制解调器，没有崩溃，插回后恢复） |
| 重启续跑 | 是 | 是（3 次 `reboot`） |
| 中文指令 | 否（改用英文别名） | 是（玩家发送） |
| 中文回复 | 否 | 是（改用 JSON 之后） |
| 产物箱快满、实机缺料、5 单排队上限、连续快速发指令 | 部分在模拟器 | 否 |

**收尾**：保存了快照但结束时没有比较；释放了电脑；程序留在电脑上运行（交付物）；工作转速恢复为 256，两条线停下。

**交给验收时注意**：程序会忽略 0.5 秒内来自同一玩家的相同文字（AI 用来防止事件重复）。A1 连续发相同的 `!状态` 时，间隔小于 0.5 秒的第二条会被有意忽略，这不算“丢失”。

## 工具的问题和处理

| 现象 | 处理 |
|---|---|
| `cct_trace` 的 `run` 传 `run_id`（摘要里的字段）时报 “not a run directory” | **已修复**：现在可以直接用 `run_id`，会在输出目录下查找 |
| fixture 的箱子容量上限是 1024，而实机保险库有 1080 格（满尺寸的保险库有 1620 格），AI 只好改小 | **已修复**：上限提高到 4096 |
| fixture 的事件参数里写中文，程序收到 `?`，但没有任何提示；AI 因此放弃了在模拟器里测中文指令 | **已修复**：摘要的 `notes` 里新增 `fixture_text`，指出是哪个字段，并说明注入 UTF-8 的写法 |
| 程序把 UTF-8 中文传给外设时，trace 里显示成 `å·…`，AI 没有认出这是乱码 | **说明已补充**：`cct_guide` 第 4 节写明这种情况，以及聊天框发中文的正确写法：`textutils.serialiseJSON({ text = msg }, { unicode_strings = true })` 加 `sendFormattedMessage…`（已在模拟器里确认 1.120.2 有这个选项）。**建议**：trace 直接给这类参数加一个解码后的提示（模拟器和 mod 都要改，见下） |
| `cct_live_lua` 只能在 shell 提示符下用，AI 为改文件停了 4 次程序 | 不改。改文件可以用 `cct_live_files`，读外设可以用 `cct_live_peripheral`，说明里都写了；可以在 Skill 里再强调一次 |
| `scripted` 不检查参数类型 | 不改。参数格式要从实机 trace 里抄，这在说明里已经写了 |

## 建议（待维护者决定）

1. **trace 标出疑似 UTF-8 的字符串**（cct-run 和 cct-live 都要改，mod 需要重新发布）：程序传给外设的字符串如果是合法的多字节 UTF-8，就在记录里加一个解码后的 `utf8` 字段。这样 AI 一眼就能看出“我把中文字节发给了外设”。
2. **Skill**：
   - 在 Advanced Peripherals 聊天框的说明里写明：发中文要用 `sendFormattedMessage…` 和 `unicode_strings`；`sendMessageToPlayer` 在 0.7.48r 上只接受前两个参数；
   - 在测试流程里加一条：程序运行时要读数，用 `cct_live_peripheral`，不要停下程序；
   - 在 fixture 的写法里加一条：注入中文指令要写成 UTF-8 字节。
3. **联合测试设计**：模拟器里应该也测“连续快速发指令”。可以在 Skill 的测试清单里加一项：并行结构要用一串间隔很短的事件来验证。

## 和联合测试 3 第 2 次比较

两次的模型和客户端相同，但任务不同（订单调度和断电恢复，对比工厂看板），所以只能粗略比较。

| 指标 | 联合测试 3 第 2 次 | 联合测试 4 第 1 次 |
|---|---|---|

| 上下文压缩 | 0 次 | 0 次 |
