# 联合测试 3：Create 工厂控制中心（模组外设 + 聊天指令 + 显示器）

这一项模拟玩家实际的玩法：用 CC 电脑监控和控制自己的 Create 工厂，并通过聊天栏和显示器跟它交互。

要测试的是：
- 面对 Skill 里没有写到的**模组外设**时，AI 会不会去查资料，并在实机上确认真实的方法，而不是凭记忆编造 API；
- 模拟器能测的部分先在模拟器里测，模组外设部分到实机上验证；
- 程序能不能在真实的工厂里稳定运行，出问题时会不会自动保护。

提示词里**故意不写外设的方法名，也不写怎么用测试工具**。AI 可以上网查资料。

## 准备（在游戏里搭一个小工厂）

| 设备 | 说明 |
|---|---|
| 动力 | 一个动力源（创造模式下用创造马达即可）→ **转速控制器**（Rotation Speed Controller）→ 传动杆，接几台耗应力的机器（例如 2～3 台石磨或动力辊压机），并放一个 **应力表**（Stressometer）和一个 **转速表**（Speedometer） |
| 物料 | 一个**输入箱**放原料（例如圆石、小麦），用漏斗或传送带送进机器；一个**产物箱**（或 Create 保险库）收集产物 |
| 电脑 | 一台**高级电脑**，旁边接一块高级显示器（至少 3×2 格）；用有线调制解调器和网线把转速控制器、应力表、转速表、两个箱子连到电脑上（右键调制解调器，让它们变红） |
| AP 外设 | 用网线连上 Advanced Peripherals 的**聊天框**（Chat Box）和**玩家探测器**（Player Detector） |
| 工具 | 最新的 cct-run、cct-live mod、Skill；`files.allow_write = true` |
| 对话 | 新开一个对话 |

不需要搭得和下面一模一样，AI 应该自己去确认外设的名字和数量。

## 提示词

把 `<ID>` 换成电脑的 ID，`<我的ID>` 换成你的游戏名：

```text
帮我写一个 CC: Tweaked 程序：Create 工厂控制中心。

【环境】
Minecraft 1.20.1，Forge，CC: Tweaked 1.120.2。装了 Create 6.0.8、Advanced Peripherals 0.7.48r，
以及 CC:C Bridge、Tom's Peripherals 等 CC 扩展。
我在 <ID> 号电脑上用有线网络连接了：Create 的转速控制器、应力表、转速表，一个原料输入箱，一个产物箱，
还有 Advanced Peripherals 的聊天框和玩家探测器。电脑旁边有一块高级显示器。
这些外设具体有哪些方法、事件，以你在游戏里实际看到的为准；需要的话可以上网查资料。

【要做什么】
1. 显示器看板（每秒刷新）：
   - 应力：已用 / 总量和百分比，用进度条表示，超过 80% 变黄，超过 95% 变红；
   - 当前转速和目标转速；
   - 原料剩余数量、产物数量，以及最近 10 分钟每分钟的产量；
   - 工厂状态：运行 / 暂停 / 过载保护 / 缺料。
   看板上有触摸按钮：“启动 / 暂停”、“加速”、“减速”。
2. 自动保护：
   - 应力超过 95% 时自动降低转速，直到回到安全范围，并记录这次保护；
   - 原料用完时自动暂停，补料后自动恢复；
   - 产物箱快满（超过 90%）时自动暂停。
3. 聊天指令（通过聊天框）：
   - 我在聊天栏输入 `!工厂 状态`，程序用聊天框只回复给我一条简短的状态；
   - `!工厂 启动`、`!工厂 暂停`、`!工厂 转速 64`：控制工厂；
   - 只接受 <我的ID> 的指令，其他人发的指令回复“没有权限”。
   转速要限制在安全范围内，超出范围要拒绝并说明。
4. 通知：发生过载保护、缺料、产物箱快满时，如果我在线，就用聊天框私聊通知我。
   同一件事 5 分钟内不要重复通知。注意聊天框有发送频率限制。
5. 玩家探测器：看板上显示我是否在工厂附近（16 格内）。我不在附近时，“加速”按钮不可用（防止别人乱按）。
6. 运行日志：保护、指令、状态变化写进日志文件，文件太大时自动轮换，只保留最近两份。
7. 设置（转速范围、阈值、玩家名等）放在配置文件里，第一次运行时自动生成。

【要求】
- 外设断开（例如有人拆掉了应力表）时程序不能崩溃：看板上标出哪个外设不在线，重新接上后自动恢复。
- 看板刷新、聊天指令、自动保护要同时工作，互不阻塞。
- 开机自动运行，但不要覆盖我现有的 startup.lua。

【交付与测试】
写好之后先测试，再部署到我游戏里的 <ID> 号电脑上运行，确认看板、按钮、聊天指令和自动保护都正常。
<ID> 号电脑可以接管，可以在上面创建和修改文件（不要覆盖 startup.lua）；测试时可以改变工厂的转速、启动和暂停工厂。
需要我在游戏里配合（比如在聊天栏输入指令、拿走原料、加机器制造过载）时，告诉我具体做什么，等我做完再继续。
测完把电脑上与本程序无关的改动恢复原样，把工厂恢复到测试前的转速，然后释放。
最后告诉我：
- 每个外设实际用到了哪些方法，你是怎么确认的（查到的资料，以及在游戏里的验证）；
- 哪些在模拟器里测过、哪些在游戏里测过、哪些没测到。
```

## 需要观察

**查资料和确认 API（重点）**
- 有没有在写代码之前，先在实机上查清外设的名字、类型和方法（例如 `peripheral.getNames`、`peripheral.getType`、`peripheral.getMethods`）；
- 上网查到的资料和游戏里实际的方法不一致时，是否以游戏里的为准，并说明差异；
- 有没有编造不存在的方法；
- 聊天框的事件名、参数、发送频率限制，是查过、在实机上验证过，还是凭记忆写的。

**设计**
- 是否先拆解需求、确认布局，并给出默认假设（例如转速范围、什么算“快满”）；
- 看板、聊天、自动保护是否放在并行的结构里，没有一处阻塞其他部分；
- 外设断开时是怎么处理的（每次调用前检查，还是用 `pcall` 包起来）；
- 自动保护会不会和玩家的手动指令冲突（比如过载时玩家又要求加速）。

**测试**
- 是否用模拟器测了能测的部分：看板排版、触摸按钮、物品计数和产量统计、配置文件、日志轮换、外设断开的处理（fixture 里去掉外设）。模组外设部分有没有用替身（自己写的模拟函数或 fixture）来测逻辑；
- 是否明确说明模拟器测不了哪些（Create 和 AP 的外设、聊天框、真实的应力变化）；
- 实机上：
  - 有没有用 trace 的 `peripheral_call` / `peripheral_return` 核对实际的调用和返回值；
  - 有没有请你配合测试聊天指令和过载保护，而不是跳过；
  - 有没有用 `cct_live_snapshot` 在改动前保存、结束时恢复；测完有没有把转速恢复原样。

**结果**
- 看板、按钮、聊天指令、自动保护在实机上是否都能工作；
- 拆掉一个外设再接回去，程序是否正常；
- 测完后电脑上是否只剩本程序的文件，`/.cctlive` 是否为空，工厂转速是否恢复。
