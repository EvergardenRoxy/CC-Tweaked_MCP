# 联合测试 4：Create 订单产线（两条产线 + 订单队列 + 断电恢复）

联合测试 3 的两次运行都卡在同一个问题上：外设调用期间到达的事件被 CC 丢弃。第 2 次在这里花了约 34 分钟，交付的程序仍然会丢指令。之后 cct-run 0.2.0 和 Skill 1.2.0 针对这些问题做了改进，但这些改进还没有经过 AI 实测：
- 模拟器的 `scripted` 外设和 `contains` 过滤；
- 实机的 `cct_live_peripheral` 和只读 `/rom`；
- Skill 里“用 `parallel` 分开轮询和事件处理”的默认结构。

这一轮的任务比联合测试 3 更复杂，并且**由维护者在 AI 结束后做独立验收**，不只看 AI 自己的报告。

## 这一轮要回答的问题

| 编号 | 问题 | 怎么判断 |
|---|---|---|
| Q1 | 有了 Skill 1.2.0，AI 会不会**一开始**就把轮询外设和处理事件分开，而不是等到实机丢指令了才发现 | 第一版代码的结构；花在“指令丢失 / 看板冻结”上的时间（联合测试 3 第 2 次约 34 分钟）；验收 A1 |
| Q2 | AI 会不会在模拟器里用 `scripted` 描述 Create 和 AP 的外设，并且数值取自实机，而不是自己写 Lua 替身 | 会话里的 fixture；数值是否和 `cct_live_peripheral` 或 trace 里的返回值一致 |
| Q3 | 程序运行时，AI 会不会用 `cct_live_peripheral` 和 trace 的过滤（`contains`、`peripheral`、`method`）来核对，而不是停下程序再用 `cct_live_lua` | 工具调用统计 |
| Q4 | AI 会不会自己发现 Create 的“反直觉”行为（见下面的“埋点”），而不是凭想象写代码 | 报告里有没有提到；代码是否正确处理 |
| Q5 | 需要持久化的状态（订单队列、进度）在重启后能不能正确恢复，不重复计数、不丢订单 | 验收 A4 |
| Q6 | 和联合测试 3 相比，token、时间、工具调用和请玩家配合的次数有什么变化 | 记录表 |

**控制变量**：第 1 次用和联合测试 3 第 2 次相同的模型（deepseek-v4.1-flash，官方 API）和客户端（DeepSeek Harness），这样主要的变化就是工具和 Skill 的版本。条件允许的话，第 2 次换一个更强的模型作对照。

## 准备

### 工具

| 项目 | 要求 |
|---|---|
| cct-run | **0.2.0**，MCP 已配置，设置了 `CCT_LIVE_DIR` |
| cct-live | **0.2.0**；`files.allow_write = true`，`lease_seconds = 1800` |
| Skill | **1.2.0**（`minecraft-cc-tweaked`） |
| 确认 | 对 AI 说“列出 cct-run 的工具”，应该看到 20 个，包括 `cct_live_peripheral` |
| 对话 | 新开一个对话；能导出会话记录最好（用来统计时间和工具调用） |

### 在游戏里搭建

| 设备 | 说明 |
|---|---|
| 动力 | 一个动力源 → **转速控制器** → 主传动轴，接一个**应力表**和一个**转速表**。动力源的应力容量要设置成**只够一条产线全速运行，两条同时全速会过载** |
| A 线：压板 | 主轴 → **离合器**（Clutch）→ 辊压机，原料箱 A 放铁锭，产物送进产物保险库 |
| B 线：磨粉 | 主轴 → **离合器** → 石磨（或粉碎轮），原料箱 B 放小麦，产物送进同一个产物保险库 |
| 离合器控制 | 两个离合器分别由电脑的**两个面的红石输出**控制（直接相邻，或用 Create 的红石链接转发） |
| 显示 | 电脑旁一块高级显示器（至少 3×2 格）；另外放一个 **Display Link（显示链接器）+ 显示板**（Display Board，至少 3×2），显示链接器用网线连到电脑 |
| 物料箱 | 原料箱 A、原料箱 B、产物保险库（Create Vault），全部用网线连到电脑 |
| AP 外设 | **聊天框**、**玩家探测器**，用网线连到电脑 |
| 电脑 | 一台高级电脑，电脑上已有一个和本程序无关的 `startup.lua`（例如只打印一行字） |

搭完记下：电脑 ID、离合器在电脑的哪两面、动力源的应力容量、每条线全速时的应力。**这些信息不要告诉 AI**，让它自己去确认。

### 埋点（不告诉 AI，用来观察 Q4）

这些都是游戏的真实行为，不是故意设的错误：

1. **离合器通红石后是断开的**：输出红石 = 停止这条线。凭直觉写的程序会把开和关弄反。
2. **两条线不能同时全速**：动力源的容量只够一条。程序要根据应力决定能不能并行，或者降速并行。
3. **显示链接器写入后要刷新才会显示**，而且显示板的大小有限（以实机为准，AI 应该自己查实）。
4. **转速带符号**，方向不同时是负数；**保险库的格子数**和普通箱子不同。
5. **聊天框有发送频率限制**，连续回复太快时会失败。
6. **指令是中文的**：聊天框事件里普通的 `message` 参数中，中文会变成 `?`，要用 `messageUtf8`（联合测试 3 第 2 次遇到过）。
7. 电脑上已有一个 `startup.lua`，不能覆盖。

## 提示词

把 `<ID>` 换成电脑的 ID，`<我的ID>` 换成你的游戏名：

```text
帮我写一个 CC: Tweaked 程序：Create 订单产线控制器。

【环境】
Minecraft 1.20.1，Forge，CC: Tweaked 1.120.2。装了 Create 6.0.8、Advanced Peripherals 0.7.48r。
<ID> 号电脑控制两条产线：A 线（辊压机，铁锭 → 铁板）和 B 线（石磨，小麦 → 面粉），共用一个动力源。
每条线前面有一个离合器，由电脑的红石输出控制；动力源后面有转速控制器、应力表和转速表。
两条线各有一个原料箱，产物都进同一个产物保险库。
电脑旁边有一块高级显示器，还用网线连了一个显示链接器（接着一块显示板）、聊天框和玩家探测器。
外设的名字、方法、事件，离合器在哪两面、怎么控制，都以你在游戏里实际看到的为准；需要的话可以上网查资料。

【要做什么】
1. 订单（通过聊天框）：
   - `!订单 铁板 64`、`!订单 面粉 128`：下一个订单，回复订单编号；最多排队 5 个；
   - `!订单 列表`：列出排队中的订单和当前进度；
   - `!订单 取消 <编号>`：取消订单（正在生产的也可以取消，取消后停下对应的产线）；
   - `!状态`：一条简短的总体状态。
   只接受 <我的ID> 的指令，其他人回复“没有权限”。数量、产品名不合法时说明原因。
2. 生产：
   - 按订单开启对应的产线，以订单开始时产物保险库里该产物的数量为基准计数，达到数量后关闭产线，并私聊通知我；
   - 应力允许时 A、B 两条线可以同时生产；不允许时按顺序生产，或者降低转速后同时生产，你来决定并说明理由；
   - 应力超过 95% 时立即降速或关闭一条线，回到安全范围后恢复；
   - 原料用完时暂停这个订单并通知我，补料后自动继续；产物保险库快满（超过 90%）时全部暂停。
3. 显示：
   - 显示板（通过显示链接器）：订单队列和每个订单的进度，给远处的人看；
   - 显示器：应力（进度条，超过 80% 变黄，超过 95% 变红）、转速、两条线各自的状态、原料剩余、最近 10 分钟每分钟的产量；
   - 显示器上的触摸按钮：“全部暂停 / 继续”、“取消当前订单”。我不在附近（16 格内）时，按钮不可用。
4. 可靠性：
   - 订单队列和进度保存在文件里。电脑重启、区块卸载、我退出再进入世界之后，程序自动继续，不能丢订单，不能把重启前已经生产的数量算错；
   - 外设断开时不能崩溃：显示哪个外设不在线，接回后自动恢复；离合器所在的面不受影响时，产线要能安全停下；
   - 任何时候聊天指令都要在 2 秒内回复，一条都不能丢，包括产线正在运行、看板正在刷新、我连续快速发好几条的时候。
5. 运行日志写进文件，太大时自动轮换，只保留最近两份。设置（玩家名、阈值、转速范围、离合器的面等）放在配置文件里，第一次运行时自动生成。
6. 开机自动运行，但不要覆盖我现有的 startup.lua。

【交付与测试】
写好之后先测试，再部署到我游戏里的 <ID> 号电脑上运行，确认订单、两条产线、保护、显示和断电恢复都正常。
<ID> 号电脑可以接管，可以创建和修改文件（不要覆盖 startup.lua）；测试时可以开关产线、改变转速、重启电脑。
需要我在游戏里配合（发聊天指令、拿走原料、拆掉外设、退出再进入世界等）时，告诉我具体做什么，等我做完再继续。
交付时附上可以重复运行的自动化测试，说明怎么运行。
测完把电脑上与本程序无关的改动恢复原样，把转速恢复到测试前，关闭两条产线，然后释放。
最后告诉我：
- 每个外设实际用到了哪些方法，你是怎么确认的；有没有和你最初的预期不一样的地方；
- 哪些在模拟器里测过、哪些在游戏里测过、哪些没测到；
- 你认为这个程序还有哪些风险。
```

## 需要观察

**结构（Q1）**
- 第一版代码是否就把轮询外设、处理事件、刷新显示分开（`parallel` 或等价结构），还是写成一个循环；
- 如果写成了一个循环，是在模拟器里、在实机上还是在维护者验收时才发现的；
- 聊天框回复是否考虑了频率限制；接收中文指令时是否用了 `messageUtf8`。

**模拟器（Q2）**
- 是否用 fixture 的 `scripted` 外设描述了转速控制器、应力表、聊天框等，而不是自己写 Lua 替身；
- fixture 里的数值是否取自实机（`cct_live_peripheral`、trace 的返回值）；
- 是否用时间线的 `method` 动作模拟应力上升、原料用完；是否在模拟器里模拟了重启恢复（预置文件 + 运行）；
- 是否用 `cct_trace` 的 `contains` 或 `peripheral` 过滤查看调用。

**实机（Q3、Q4）**
- 程序运行时，是否用 `cct_live_peripheral` 读应力、库存来核对，而不是停下程序；
- 是否读过 `/rom`（例如查 `parallel` 的实现）；
- 埋点 1～6 里，AI 自己发现了哪几个，是怎么发现的；有没有写错后才改；
- 有没有用 `cct_live_snapshot` 在改动前保存、结束时比较；请玩家配合了哪些项目。

**报告**
- 报告里的“已测”是否和会话里的实际操作一致（抽查 3 条，对照 tick 或 seq）；
- 列出的风险里，有没有包含维护者验收中实际不通过的项目。
