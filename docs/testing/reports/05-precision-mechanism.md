# 精密构件自动化测试核验（测试3.zip）

依据：用户上传的 `测试3.zip`（程序、测试、交付说明与设备状态）和 DSH 会话导出，以及用户补充的会话用量统计。时间统一为 **2026-10-19，Asia/Seoul**。

**结论：修改后的单机械手方案确实跑通了真实五轮加工、失败分流、按成品补产及选定位置的恢复；尚不能认定全部可靠性验收通过。交付程序仍有可复现的持久化、发送结果与队列处理问题。** 原有三套测试在本次复核中再次全部通过，但没有覆盖这些边界。

本次仅分析上传证据并在 Linux cct-run 0.2.4 / CC:T core 1.120.2 / Java 17 中复跑代码；未连接用户游戏、未改动用户存档，也没有重新执行 NeoForge 客户端实测。六个新增探针针对上传的 Lua 控制程序。证据与复现方法见 [results-joint-test5](../../../issues_to_fix/evidence/dynamic/results-joint-test5/README.md)。

## 有哪些结果能确认

### 配方与真实加工

seq 311 从本地 Create jar 读出的基础配方包含三步序列、`loops=5`，结果权重合计 150，精密构件权重 120，得到 **80%**。这是整件结束时的权重，五轮不是五次独立的 80% 判定。该配方有 9 类最终结果，即 1 类成功与 8 类失败；交付 README 所称“其他 9 种结果”多算了一种，程序白名单额外包含大齿轮。

没有服务器最终 recipe manager/数据包覆盖导出，因此精确概率的直接证据是 jar 基础配方；真实运行的成功比例本身不证明概率。工件五轮加工、真实精密构件和副产物的入库均有会话读数和日志支持。

| 场景 | 可核实结果 | 边界 |
|---|---|---|
| R002，目标 8，上限 20 | 10 次尝试、8 成功、2 失败；seq 2733 的真实状态读回为 done/10/8/2 | 不是用 `投入×0.8` 算出的成品数 |
| R003，固定 3 次 | 会话演练/交付记录为 3 次成功 | 小样本全成功并不违反 80% |
| R004，电脑重启 | 日志中在第二轮后有 `boot: recovery: resume attempt`，后续第三至五轮继续；两次终态分别为安山合金和时钟 | 证明所选检查点恢复，不证明任意崩溃位置都能无歧义恢复 |
| R005，暂停/继续/取消 | 日志有暂停、继续、第一件成功、第二件中途取消；半成品移入副产物库单列 | 取消留下的半成品不是随机失败结果 |
| R006，重复订单 | 玩家按要求真实重发同 ID，回复未重复下单，并仅完成一次尝试 | 不等于永久保留所有历史 ID；代码有 40 条记录上限 |
| R007，缺料 | 大齿轮为 0 时新单暂停、金板尚未投入；补料后完成一次，终态是时钟 | 这是**开工前缺料**，不能写成“第三轮中途缺料恢复已实测” |
| R008，退出/重进世界 | 用户确认自动恢复，日志在第 2 次尝试第二轮后记录启动恢复，最后 12 次/8 成功/4 失败，辅料各 60 份 | 不是第五轮消费与终态转移的崩溃窗口测试 |
| R009，次数上限 | 实际运行 5 次，3 成功/2 失败，缺 2 件后停下 | 原输入是 `5 1`，旧版静默抬到 5；最终版已改为拒绝上限小于目标的参数，未按原样完成“只投一次”演练 |
| R010，depot 预占 | depot 中 64 个大齿轮导致未投料即暂停；清空后继续完成一次 | 这是进料前占用，不是成品库/副产物库满时的结算阻塞 |
| 最终状态与收尾 | 成品 25，副产物库物品 13，depot/deployer 均为空；seq 4326 实际 detach 成功 | `device-final.txt` 保存于释放前，attached=true 与之后释放不矛盾；副产物库件数不能直接当失败次数 |

11 个交付 Lua 文件与会话里对相应游戏文件的**最后一次写入载荷逐字节一致**；这比只比字节数更强，但仍不是对当前游戏磁盘的重新读取。全局金板/辅料库存受玩家补料和故障演练取放影响，不能只凭最终总库存推算全部材料消耗。

### 中文与显示

真实聊天输入/中文回复有玩家回答及截图支持；翻牌屏中文也有照片和 seq 1811 的玩家确认。用户追加的中文库存显示有对应代码与现场显示验证。CC 高级显示器仍用英文，不违反本轮要求。

需要纠正交付说明中的两项结论：

1. **`getSize()` 不是“不可信”**。seq 1302 反汇编明确先返回 `maxRows()`，再返回 `maxColumns()`。`8,17` 就是 8 行、17 列；把它当成“宽 8、高 17”导致了错误布局。现场照片与这个返回值一致。
2. **“每行必须一个显示链接器”没有证据支持**。同一实例的光标/写入接口维护多行内容，会话也用同一实例写出了 8 行。应记录实际来源、目标起始行和多行输出能力，不能把这次 GUI/链路设置问题概括为通用限制。

字节表传给 `writeBytes`、JSON Unicode 转义传给 AP formatted-message 的做法有实现记录和现场效果支持。直接把 UTF-8 文本传给 Java 字符串接口会出现乱码，不能把这种现象一概归为屏幕缺字。

## 三套测试复跑与覆盖缺口

| 脚本 | 上传记录 | 本次复跑 |

合计是 **3 个测试脚本、310 条断言**，不是 310 个独立实机测试。上传 fixture 与交付模块内容一致，可复现。

fixture 只预置 Lua 文件，未声明 `scripted` 外设。测试通过 `mockhw.lua` 注入假硬件层，适合检查状态机、布局和正常恢复，但不验证真实 `hw.lua` 的发送语义、完整事件调度或真实装配物理。比如发送失败测试直接替换 Mock 的 `chat_send` 返回 false，绕过了真实适配器；因此没有发现真实适配器把 false 包装成成功的问题。

主要未覆盖/不应扩大解释的项目：

- 实机第三轮中途缺辅料、成品/副产物输出满、真实转移返回 0。
- 第五轮消费/终态转移前后的任意重启；损坏文件和持久化失败。
- 10 个不同请求 ID 的真实突发输入及 2 秒确认延迟测量。app 测试主要重复查询同一订单，并把冷却设为 0；不等价于实际 1.5 秒节流下的请求完整性。
- 实机关键外设离线：用户明确跳过；模拟器的缺库错误确实有测试。
- trace 轮换、真实区块卸载和不同 recording 模式：本次没有完整验收记录。

交付 README 的“实机未测”主要只列断线，范围写窄了，应补上这些边界。不能据此抹掉已经跑通的生产流程，也不能把生产流程跑通等同于所有故障矩阵通过。

另有文档边界：`LOG_MAX=120` 限制的是 state.log；`events.log` 一直 append，上传文件已超过 120 行，没有轮换实现。README 的“日志 120 行”应说清是哪份日志。本轮实际提示词没有单独要求定额日志轮换，故不按旧方案额外判违约。

## 会话中的误判和效率

**库存误读可以明确归因。** seq 3438 的 `cct_live_peripheral list` 结果只保留 50 个条目，末尾标 `"...":"101 more"`。AI 相加得到齿轮 1572、铁粒 1573，进而问玩家是否移走大量物料；玩家指出实际是 4836/4773。这里是把预览当成完整列表，不是库存凭空消失。应从完整列表在游戏内聚合，或使用明确支持的汇总能力，不能对被截断结果做全量对账。

其他可核对事项：

- 开头的 Windows ACL `grantWrite` 失败属于客户端环境；PowerShell 两次尝试直接 Expand-Archive .jar 失败属于调用方法问题，之后转为 ZIP 才解开，均不是加工程序的结果。
- 显示排查中，用户已经说明支持中文，AI 仍将 CC 显示器的字库限制泛化到 Create 显示板，并把 8 行/17 列反读。18:39–19:03 的窗口主要在处理中文、链接器、尺寸和刷新，也穿插了测试，不能全部精确归为纯显示耗时。
- 多次 trace 查询没有推进 after/offset，读回相同早期事件；会话出现重复工具提醒。末段 seq 4182–4312 有 12 次 cct_run，其中多轮相同测试组是在取结果/写交付记录，不能重复计成新覆盖。
- R009 的“上限 1 被偷偷改成 5”是真实旧版问题，截图与日志吻合；最终源码和新测试已改为明确拒绝，不应再当作当前未修复缺陷，也不能把修前演练包装成正确执行了原上限。

## 下一轮优先验证什么

先修并复测存储三项：更新备份、区分首次启动与损坏状态、持久化失败时停止新的物料动作。再修发送结果判断、队列拒绝/确认与日志调用，并以真实适配器和非零冷却复测。显示尺寸按行/列协议处理，保留现场配置，不把实现约定写成 API 故障。

之后只补缺少的实机边界：第三轮断辅料、成品/副产物满库、终态转移附近重启、带唯一 ID 的连续中文查询及回复核对。用户跳过的断线项继续明确标记，后续有授权和条件时再测。保留首轮失败和修后结果，不用新的通过覆盖本轮记录。
