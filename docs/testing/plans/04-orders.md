# 联合测试 4：Create 订单产线（订单队列 + 断电恢复 + 不丢指令）

联合测试 3 的两次运行都卡在同一个问题上：外设调用期间到达的事件被 CC 丢弃。第 2 次在这里花了约 34 分钟，交付的程序仍然会丢指令。之后 cct-run 0.2.0 和 Skill 1.2.0 针对这些问题做了改进，但这些改进还没有经过 AI 实测：
- 模拟器的 `scripted` 外设和 `contains` 过滤；
- 实机的 `cct_live_peripheral` 和只读 `/rom`；
- Skill 里“用 `parallel` 分开轮询和事件处理”的默认结构。

这一轮**沿用联合测试 3 的工厂**（不需要改产线布局），任务换成更复杂的订单调度和断电恢复，并且**由维护者在 AI 结束后做独立验收**，不只看 AI 自己的报告。

## 这一轮要回答的问题

| 编号 | 问题 | 怎么判断 |
|---|---|---|
| Q1 | 有了 Skill 1.2.0，AI 会不会**一开始**就把轮询外设和处理事件分开，而不是等到实机丢指令了才发现 | 第一版代码的结构；花在“指令丢失 / 看板冻结”上的时间（联合测试 3 第 2 次约 34 分钟）；验收 A1 |
| Q2 | AI 会不会在模拟器里用 `scripted` 描述 Create 和 AP 的外设，并且数值取自实机，而不是自己写 Lua 替身 | 会话里的 fixture；数值是否和 `cct_live_peripheral` 或 trace 里的返回值一致 |
| Q3 | 程序运行时，AI 会不会用 `cct_live_peripheral` 和 trace 的过滤（`contains`、`peripheral`、`method`）来核对，而不是停下程序再用 `cct_live_lua` | 工具调用统计 |
| Q4 | AI 会不会自己发现 Create 和 AP 外设的“反直觉”行为（见下面的“埋点”），而不是凭想象写代码 | 报告里有没有提到；代码是否正确处理 |
| Q5 | 需要持久化的状态（订单队列、进度）在重启后能不能正确恢复，不重复计数、不丢订单 | 验收 A4 |
| Q6 | 和联合测试 3 相比，token、时间、工具调用和请玩家配合的次数有什么变化 | 记录表 |

**控制变量**：第 1 次用和联合测试 3 第 2 次相同的模型（deepseek-v4.1-flash，官方 API）和客户端（DeepSeek Harness），这样主要的变化就是工具和 Skill 的版本。条件允许的话，第 2 次换一个更强的模型作对照。

### 在游戏里搭建

直接用联合测试 3 搭好的工厂即可，只需确认下面几点：

| 设备 | 说明 |
|---|---|
| 动力 | 动力源 → **转速控制器** → 传动杆，接 2～3 台耗应力的机器（石磨或辊压机），以及**应力表**和**转速表**。确认把转速调到最高时**应力会超过 100%**（不够的话多接一台机器），这样过载保护才有东西可测 |
| 物料 | 一个**原料箱**（放两种原料，例如圆石和小麦，或铁锭和小麦），一个**产物箱或 Create 保险库** |
| 显示 | 电脑旁一块高级显示器（至少 3×2 格） |
| AP 外设 | **聊天框**、**玩家探测器** |
| 连接 | 转速控制器、应力表、转速表、两个箱子、聊天框、玩家探测器都用有线调制解调器和网线连到电脑 |
| 电脑 | 一台高级电脑，上面已有一个和本程序无关的 `startup.lua`（例如只打印一行字） |
| 可选：显示链接器 | 见下面“可选：显示链接器”。没有就跳过，并删掉提示词里标了【可选】的那一行 |

产线的开和停**只靠转速控制器**：目标转速设为 0 就停，设为正常转速就开。不需要离合器，不用改布局。

搭完记下：电脑 ID、正常运行的转速、转速调到多少时应力超过 95%。**这些信息不要告诉 AI**，让它自己去确认。

### 可选：显示链接器（Display Link）

显示链接器是 **Create 自带的一个方块**（Create 的机械动力物品栏里，图标像一个带小天线的黄铜底座）。它平时的用法是：一头贴在某个“数据源”上（比如一个箱子），另一头指向一个显示目标（比如告示牌，或者 Create 的**显示板 Display Board**，一种可以拼成大块的黄色信息板），把数据源的信息显示到目标上。

装了 CC: Tweaked 之后，显示链接器**用有线调制解调器连到电脑**时，就变成电脑的一个外设：电脑可以直接往它指向的显示目标上写文字。这相当于“Create 风格的远程显示屏”，挂在工厂远处给别人看订单进度。

放法：
1. 放一块显示板（至少 3 宽 × 2 高，用几块显示板拼起来）；
2. 拿着显示链接器先**右键显示板**（选定目标），再把显示链接器放在附近任意位置；
3. 在显示链接器上贴一个有线调制解调器，用网线连到电脑，右键调制解调器让它变红。

它值得测的原因：这是一个 Skill 里没写过的模组外设，而且有“写入后要刷新才显示”“显示板大小有限”这类只有在实机上才能发现的行为。但它**不是这一轮的重点**，搭起来麻烦的话可以不要。

### 埋点（不告诉 AI，用来观察 Q4）

这些都是游戏的真实行为，不是故意设的错误：

1. **转速越高应力越大**：把转速调到最高会过载。“开工”不能简单地设成最高速；过载保护降速时还要考虑玩家刚刚下的转速指令。
2. **转速带符号**：方向不同时是负数；目标转速和实际转速可能不一样（还在加速，或者过载停转）。
3. **保险库的格子数**和普通箱子不同，“快满”要按实际容量算。
4. **聊天框有发送频率限制**：连续回复太快时会失败。
5. **指令是中文的**：聊天框事件里普通的 `message` 参数中，中文会变成 `?`，要用 `messageUtf8`（联合测试 3 第 2 次遇到过）。
6. **电脑上已有一个 `startup.lua`**，不能覆盖。
7. （可选）**显示链接器写入后要刷新才会显示**，而且显示板的大小有限（以实机为准）。

## 提示词

把 `<ID>` 换成电脑的 ID，`<我的ID>` 换成你的游戏名：

```text
帮我写一个 CC: Tweaked 程序：Create 订单产线控制器。

【环境】
Minecraft 1.20.1，Forge，CC: Tweaked 1.120.2。装了 Create 6.0.8、Advanced Peripherals 0.7.48r。
我在 <ID> 号电脑上用有线网络连接了一条 Create 产线：转速控制器、应力表、转速表，一个原料箱（放了两种原料），
一个产物箱（或保险库），还有 Advanced Peripherals 的聊天框和玩家探测器。电脑旁边有一块高级显示器。
【可选】网络上还有一个 Create 的显示链接器，指向一块显示板。
产线没有单独的开关：转速控制器的目标转速设为 0 就停，设为工作转速就开。
外设的名字、方法、事件，原料和产物分别是什么，都以你在游戏里实际看到的为准；需要的话可以上网查资料。

【要做什么】
1. 订单（通过聊天框）：
   - `!订单 <产品> <数量>`（例如 `!订单 面粉 64`）：下一个订单，回复订单编号；最多排队 5 个。
     产品用中文名，中文名和物品 ID 的对应写在配置文件里，按产物箱里实际出现的物品生成默认值；
   - `!订单 列表`：列出排队中的订单和当前进度；
   - `!订单 取消 <编号>`：取消订单（正在生产的也可以取消）；
   - `!转速 <数值>`：修改工作转速，超出安全范围或会导致过载时拒绝并说明；
   - `!状态`：一条简短的总体状态。
   只接受 <我的ID> 的指令，其他人回复“没有权限”。数量、产品名不合法时说明原因。
2. 生产：
   - 订单按顺序生产：开工（设为工作转速），以订单开始时产物箱里该产物的数量为基准计数，达到数量后完成并私聊通知我；
     没有订单时停工（转速 0）；
   - 应力超过 95% 时立即降速，回到安全范围后恢复，并记录这次保护；保护期间收到的转速指令怎么处理，你来决定并说明；
   - 当前订单的原料用完时暂停这个订单并通知我，补料后自动继续；产物箱快满（超过 90%）时停工。
3. 显示：
   - 显示器：订单队列和当前订单的进度；应力（进度条，超过 80% 变黄，超过 95% 变红）；目标转速和实际转速；
     产线状态（生产 / 停工 / 暂停 / 过载保护 / 缺料）；原料剩余；最近 10 分钟每分钟的产量；
   - 【可选】显示板（通过显示链接器）：订单队列和进度，给远处的人看；
   - 显示器上的触摸按钮：“全部暂停 / 继续”、“取消当前订单”。我不在附近（16 格内）时，按钮不可用。
4. 可靠性：
   - 订单队列和进度保存在文件里。电脑重启、区块卸载、我退出再进入世界之后，程序自动继续，不能丢订单，不能把重启前已经生产的数量算错；
   - 外设断开时不能崩溃：显示哪个外设不在线，接回后自动恢复；读不到应力时不能盲目提速；
   - 任何时候聊天指令都要在 2 秒内回复，一条都不能丢，包括产线正在运行、看板正在刷新、我连续快速发好几条的时候。
5. 运行日志写进文件，太大时自动轮换，只保留最近两份。设置（玩家名、阈值、工作转速和转速范围、产品名对应等）放在配置文件里，第一次运行时自动生成。
6. 开机自动运行，但不要覆盖我现有的 startup.lua。

【交付与测试】
写好之后先测试，再部署到我游戏里的 <ID> 号电脑上运行，确认订单、生产计数、保护、显示和断电恢复都正常。
<ID> 号电脑可以接管，可以创建和修改文件（不要覆盖 startup.lua）；测试时可以开停产线、改变转速、重启电脑。
需要我在游戏里配合（发聊天指令、拿走原料、拆掉外设、退出再进入世界等）时，告诉我具体做什么，等我做完再继续。
交付时附上可以重复运行的自动化测试，说明怎么运行。
测完把电脑上与本程序无关的改动恢复原样，把转速恢复到测试前，然后释放。
最后告诉我：
- 每个外设实际用到了哪些方法，你是怎么确认的；有没有和你最初的预期不一样的地方；
- 哪些在模拟器里测过、哪些在游戏里测过、哪些没测到；
- 你认为这个程序还有哪些风险。
```

## 需要观察

**结构（Q1）**
- 第一版代码是否就把轮询外设、处理事件、刷新显示分开（`parallel` 或等价结构），还是写成一个循环；
- 如果写成了一个循环，是在模拟器里、在实机上还是在维护者验收时才发现的；
- 聊天框回复是否考虑了频率限制；接收中文指令时是否用了 `messageUtf8`。

**模拟器（Q2）**
- 是否用 fixture 的 `scripted` 外设描述了转速控制器、应力表、聊天框等，而不是自己写 Lua 替身；
- fixture 里的数值是否取自实机（`cct_live_peripheral`、trace 的返回值）；
- 是否用时间线的 `method` 动作模拟应力上升、原料用完；是否在模拟器里模拟了重启恢复（预置文件 + 运行）；
- 是否用 `cct_trace` 的 `contains` 或 `peripheral` 过滤查看调用。

**实机（Q3、Q4）**
- 程序运行时，是否用 `cct_live_peripheral` 读应力、库存来核对，而不是停下程序；
- 是否读过 `/rom`（例如查 `parallel` 的实现）；
- 埋点 1～7 里（7 只在搭了显示链接器时），AI 自己发现了哪几个，是怎么发现的；有没有写错后才改；
- 有没有用 `cct_live_snapshot` 在改动前保存、结束时比较；请玩家配合了哪些项目。

**报告**
- 报告里的“已测”是否和会话里的实际操作一致（抽查 3 条，对照 tick 或 seq）；
- 列出的风险里，有没有包含维护者验收中实际不通过的项目。
